# phi_scrub

A tool for identifying and scrubbing Protected Health Information (PHI) from documents, built around the HIPAA Safe Harbor de-identification rule in [45 CFR § 164.514](documents/45_cfr_164514.txt). The goal is to produce de-identified data that's safe to use for AI model training, logging pipelines, or any downstream system that can't hold PHI.

Everything runs locally: the LLM and the embedding model run in Ollama on your own GPU, and Chroma stores the regulation on disk. No document text leaves the machine.

The tool is designed to be modular. It's a CLI today, and the core functions (`find_phi`, `redact`) can be wrapped as a library, API endpoint, or pipeline step later.

---

## Disclaimer

I'm not satisfied with the results of this approach. Asking an LLM to infer which free text is PHI proved unreliable in testing: values get mislabeled, PHI near the end of a document gets missed, and the output always needs manual review. See [Known limitations](#known-limitations).

For my actual work case, this inference isn't needed. At my office, all the relevant PHI sits in XML, so de-identification can be done deterministically: pick the tags that hold PHI by tag name and redact the whole tag contents. There's no need to interpret the text inside them.

I would use that office data to train my model, but it can't be used here because of HIPAA compliance. This repo works on synthetic free-text documents instead (see `tests/`), which is the harder, inference-based version of the problem.

This project is an experiment, not a compliance tool. Its output should not be treated as de-identified data under 45 CFR § 164.514 without expert review.

---

## How it works

1. **Knowledge base (one-time setup).** The text of 45 CFR § 164.514 is chunked (`pdf_to_chunks.py`) and embedded into a [Chroma](https://www.trychroma.com/) vector database with `nomic-embed-text` (`ingest.py`).
2. **PHI detection.** `agent.py` sends the document to the LLM (`llama3.1:8b`) with a system prompt that defines each Safe Harbor identifier type, gives address and date examples, and includes a worked example. The LLM returns a JSON list of PHI findings, each with the exact text and a type. Ollama constrains the output to the `PHIReport` schema.
3. **Redaction.** Python replaces each reported value with a `[TYPE]` placeholder (for example `[NAME]` or `[SSN]`) and writes the output file. The LLM never rewrites the document, so non-PHI text such as diagnoses, medications and lab values can't be altered. Findings that don't appear verbatim in the document are skipped and listed.
4. **Regulation lookup.** The `query_phi_regulation` tool lets an agent search the Chroma knowledge base. It's currently used by the `--lookup` mode for testing retrieval. It isn't wired into the redaction run yet.

## Setup

### 1. Python environment (WSL)

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 2. Ollama (PowerShell on Windows, not WSL)

Ollama runs as a Windows-native process so it can use your GPU directly. Code running in WSL reaches it over the Windows host network.

**Install:** download from [ollama.com/download](https://ollama.com/download) and run the installer.

**Pull the models** (one time):

```powershell
ollama pull llama3.1:8b       # LLM used by agent.py
ollama pull nomic-embed-text  # embedding model for Chroma
```

One Ollama server hosts every model you've pulled. Each request names the model it wants, and Ollama loads it onto the GPU on demand. It stays loaded for 5 minutes of idle time.

| Model | Memory | Notes |
|---|---|---|
| `llama3.1:8b` | ~8 GB VRAM | Current default. Fits an 8 GB GPU at 8192 context |
| `llama3.2:3b` | ~4 GB | Faster, but poor at labeling PHI in testing |
| `mistral:7b` | ~8 GB | Alternative 7B model |
| `phi4-mini` | ~4 GB | Small Microsoft model |

**Let WSL reach Ollama.** By default Ollama listens only on `127.0.0.1`, which WSL2 can't reach. Set `OLLAMA_HOST=0.0.0.0` permanently (one time):

```powershell
[System.Environment]::SetEnvironmentVariable("OLLAMA_HOST", "0.0.0.0", "User")
```

**Start the server.** The Ollama tray app can start a server that ignores the new setting, so stop any running Ollama first, then start it from PowerShell and leave the window open:

```powershell
Get-Process -Name "ollama*" -ErrorAction SilentlyContinue | Stop-Process -Force
$env:OLLAMA_HOST = "0.0.0.0"
ollama serve
```

The startup log should say `Listening on [::]:11434`. If it says `127.0.0.1:11434`, the setting didn't take and WSL won't be able to connect. If `ollama serve` fails with "Only one usage of each socket address", another Ollama process is still running.

**Confirm from WSL:**

```bash
curl http://172.25.240.1:11434
# Ollama is running
```

`172.25.240.1` is the Windows host IP as seen from WSL. Check yours with `ip route | grep default`. If it differs, update `LLM_HOST` in both `ingest.py` and `agent.py`.

### 3. Build the Chroma knowledge base (WSL, one time)

```bash
python3 src/ingest.py
```

This embeds the 42 chunks from `45_cfr_164514_chunks.json` into Chroma as 768-dim vectors (cosine similarity) and stores them in `chroma_db/`. If the collection already has documents, the script skips ingestion. To rebuild, delete the database first:

```bash
rm -rf chroma_db/
python3 src/ingest.py
```

You only need to rebuild if you change the chunks or the embedding model. Changing the LLM doesn't affect Chroma.

### 4. Run it (WSL)

```bash
# Redact a document
python3 src/agent.py tests/simple1.txt tests/simple1_redacted.txt

# Test the RAG lookup on one question
python3 src/agent.py --lookup "Are telephone numbers considered PHI?"
```

## src/pdf_to_chunks.py

Extracts text from a PDF, strips eCFR page headers and footers, splits the text into overlapping chunks at paragraph and sentence boundaries, and writes a JSON file. Each record contains:

- `id`: stable unique identifier (`<source_filename>:<chunk_index>`)
- `text`: the chunk text that gets embedded
- `metadata`: source filename, page range, section heading, character offsets

**Usage:**

```bash
python3 src/pdf_to_chunks.py <input.pdf> <output.json> [--chunk-size 600] [--overlap 80]
```

**Example** (the settings used for the current chunks file):

```bash
python3 src/pdf_to_chunks.py \
  "documents/45 CFR 164.514 (up to date as of 10-28-2026).pdf" \
  documents/45_cfr_164514_chunks.json \
  --chunk-size 600 \
  --overlap 80
```

| Flag | Default | Description |
|---|---|---|
| `--chunk-size` | `800` | Target character length per chunk |
| `--overlap` | `100` | Characters of overlap between consecutive chunks |

---

## src/ingest.py

Loads the chunks JSON, checks that Ollama is reachable (`check_llm_connection`), skips if the collection already has data (`check_chroma_empty`), then embeds the chunks in batches of 10 with `nomic-embed-text` and stores the vectors, text and metadata in the `phi_regulations` collection.

Configuration variables at the top of the file:

| Variable | Default | Description |
|---|---|---|
| `CHUNKS_PATH` | `documents/45_cfr_164514_chunks.json` | Input chunks file |
| `DB_PATH` | `./chroma_db` | Chroma database directory |
| `COLLECTION_NAME` | `phi_regulations` | Chroma collection name |
| `EMBEDDING_MODEL` | `nomic-embed-text` | Ollama embedding model |
| `LLM_HOST` | `http://172.25.240.1:11434` | Ollama host (Windows host IP from WSL) |

Chroma runs in `PersistentClient` mode, so it's just files on disk. There's no server process; it opens and closes like SQLite.

## src/agent.py

**Redaction mode** (`<input_file> <output_file>`):

1. `find_phi()` sends the document and `SYSTEM_PROMPT` to the LLM using `with_structured_output(PHIReport)`. The reply is a list of `{value, type}` findings.
2. `redact()` replaces each value with `[TYPE]`. Longer values are replaced first, so a short value like `Austin` can't break up a longer one. Duplicates are ignored, and values that don't appear verbatim in the document are skipped.
3. `run()` writes the redacted file and prints every finding and any skipped values.

**Lookup mode** (`--lookup "<question>"`): `lookup()` builds a LangChain agent with the `query_phi_regulation` tool, asks the one question, and prints the tool call, the retrieved regulation text and the answer. Use it to check that the tool, the embeddings and Chroma are working together.

Configuration variables at the top of the file:

| Variable | Default | Description |
|---|---|---|
| `LLM_MODEL` | `llama3.1:8b` | Ollama chat model |
| `EMBEDDING_MODEL` | `nomic-embed-text` | Must match the model used by `ingest.py` |
| `LLM_HOST` | `http://172.25.240.1:11434` | Ollama host (Windows host IP from WSL) |
| `DB_PATH` | `./chroma_db` | Chroma database directory |
| `COLLECTION_NAME` | `phi_regulations` | Chroma collection name |
| `TOP_K_CHUNKS` | `5` | Regulation chunks returned per lookup |
| `NUM_CTX` | `8192` | LLM context window in tokens (Ollama's default is 4096) |
| `OUTPUT_METHOD` | `json_schema` | `json_schema` makes Ollama constrain output to the schema. `json_mode` allows any JSON and relies on the prompt for the shape |

**Placeholder types** (`PHIType`):

`NAME` · `ADDRESS` · `DATE` · `AGE` · `PHONE` · `FAX` · `EMAIL` · `SSN` · `MRN` · `HEALTH_PLAN_ID` · `ACCOUNT_NUMBER` · `LICENSE_NUMBER` · `VEHICLE_ID` · `DEVICE_ID` · `URL` · `IP_ADDRESS` · `BIOMETRIC` · `PHOTO` · `OTHER_ID`

### Known limitations

From the last full test run on `tests/simple1.txt` (before the address and date examples were added to the prompt):

- Labels were correct, and all clinical content was left intact.
- PHI near the end of the document was missed (the PCP address, zip code, phone number and next appointment date).
- Physician names weren't redacted. Strictly speaking, Safe Harbor covers the patient and their relatives, employers and household members, so whether provider names are redacted is a policy choice.
- A date reported with a time (`10/28/2026 08:15 AM`) doesn't match the same date written without one elsewhere. The prompt now asks the model to report both forms, but this hasn't been re-tested.
- `48` was labeled `[AGE]`. Ages are only PHI over 89, so this is a harmless over-redaction.
- Replacement is plain substring matching. A short value like a city name is replaced everywhere it appears, including inside facility names.
- In lookup mode, retrieval sometimes ranks the limited data set list (§ 164.514(e)(2)) above the Safe Harbor list (§ 164.514(b)(2)). `nomic-embed-text` is meant to be used with `search_query:` / `search_document:` prefixes, which aren't applied yet.

Always review redacted output before treating it as de-identified.

## Embeddings

Embeddings are generated locally by `nomic-embed-text` running in Ollama. No data leaves the machine, which is the right default for a tool handling PHI.

To switch to OpenAI embeddings, replace `OllamaEmbeddings` with `OpenAIEmbeddings` from `langchain_openai` in both `ingest.py` and `agent.py`, then rebuild `chroma_db/`. Vectors from different embedding models aren't compatible. Note that this sends text to an external API.

## HIPAA reference

The 18 Safe Harbor identifiers defined in **45 CFR § 164.514(b)(2)** are the detection targets:

Names · Geographic subdivisions smaller than a state · All elements of dates (except year) · Phone numbers · Fax numbers · Email addresses · SSNs · Medical record numbers · Health plan beneficiary numbers · Account numbers · Certificate/license numbers · Vehicle identifiers · Device identifiers · URLs · IP addresses · Biometric identifiers · Full-face photos · Any other unique identifying number, characteristic, or code
